# 实施研究：会话上下文压缩

## 输入预算

**决策**：使用 UTF-8 字节加固定封装余量做首版本地估算，并检查模型配置的窗口及预留输出。估算覆盖文本、结构化调用参数、工具结果和 schema。每次重建主请求都检查一次。

**理由**：当前的轮数限制无法防住同一轮内的大工具结果。现有 Provider 契约在响应后返回实际用量，发送前需要可离线复现的度量。分模型 tokenizer 增加依赖且难以统一，单纯按字符数除以固定比例对中文、代码和 JSON 偏差较大。UTF-8 方法会偏保守，仍可能与供应商真实计量有差异。

## 摘要与费用

**决策**：每次从已持久化游标推进，达到轮数或规模阈值才生成摘要。原文和游标通过原有 Session 保存路径写入。每次尝试有独立输入与输出配额。

**理由**：每次窗口移动立即摘要会增加请求数。逐次临时摘要无法跨重启复用。每次重发旧原文也会抵消缩窗收益。派生状态放长期记忆会改变作用域与历史隔离。

## Provider 适配验证

**决策**：复用 `OpenAiCompatibleProtocolTest` 的回环 HTTP 捕获方式，经过 `DefaultProviderService` 及仓库现有 OpenAI 兼容和 DashScope factory。分别检查 `messages[0]` / `input.messages[0]`，以及 `tools` / `parameters.tools`。验证摘要请求的工具列表为空或省略，并检查 `max_tokens` 对应位置。

**依据**：现有 `DefaultProviderService#requestPrompt` 已复制 `getMaxTokens()`。仓库锁定的适配依赖将该选项映射为各协议请求字段。协议测试比较稳定字段及顺序，实际缓存策略由供应商决定。

## 存储和兼容

**决策**：在已有 SQLite 迁移序列追加 V10，现有数据默认无摘要，既有调用默认 CHAT。已处理游标允许越过未完成的旧轮。沿用同会话串行写入和已有 Session 保存语义。

**理由**：当前 Session 完整消息本身已作为整快照写入。独立文件或摘要表会引入额外一致性边界。仓库目前只有 SQLite 迁移目录。
