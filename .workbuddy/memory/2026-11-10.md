## Agent token 开销调研（诊断，未改代码）

用户反馈 agent token 开销过大，做了根因调研。结论：主因是上下文重复计费，不是单条 prompt 过大。

证据链（代码 + `.oryxos/oryxos.db` 实测 197 条 llm_calls）：

1. **ReAct 每轮全量重建 prompt**：`ReActLoop.run()` 每次迭代调 `prompts.build()`，system+记忆+历史+工具 schema 全部重发重计费。daily-weather 一次任务 4 轮：723→1431→1561→1641 prompt tokens，合计 5356，约 69% 是重复内容。
2. **时间戳破坏前缀缓存**：`PromptBuilder` 第一条 SystemMessage 末尾拼 `ZonedDateTime.now(clock)`（秒级变化且位于最前），DeepSeek/Qwen 的 context cache 前缀命中被整段击穿，每轮全价。这是最高杠杆修复点。
3. **调度任务复用同一 Session**：`AgentScheduler` 用 `getOrCreate("scheduler","scheduler",profile)`，schedule-display 的 session 62 条消息、31 次成功调用；cron 为 `0 * * * * *`（每分钟），run_count=148。每次触发固定 ~648 prompt tokens，全天理论 93 万 tokens。
4. **maxHistoryTurns 只按用户轮数截断**，不看 token/字节；http_get 工具结果最大 1MB 可全量进历史（当前 demo 实际 ~1.2KB，架构上无上限）。
5. **142/197 调用失败（"供应商调用失败"，usage 未记录）**，Spring AI retry maxAttempts(1)，失败靠下次 cron 变相重试。

次要发现：qwen tokenizer 对同样中文 prompt 计数比 deepseek 高 ~86%（723 vs 1343）；AGENT.md/工具 schema 本身很小（基线 723 里 schema 约 170）。

建议修复优先级：①时间戳移到上下文尾部（恢复前缀缓存，业界报告 5-12x 降幅）②调度任务换新 session 或摘要压缩 ③工具结果截断+按 token 截断历史 ④修供应商失败根因 ⑤llm_calls 已有 token 字段，可加成本看板。

## 日志功能（分支 feat/file-logging，已提交 2c478cc）

第一版实现被用户要求回退（要先看方案），方案确认后建分支 `feat/file-logging` 重新实施并提交。

实现内容：
- `BootCliRuntime` 的 `application()`/`startServlet()` 注入默认属性：`logging.file.name=${oryxos.workspace}/logs/oryxos.log` + rollingpolicy（20MB/文件、14 天、200MB 总量、gz、启动清理）；查询类入口不落盘；外部 yaml 可逐键覆盖。

- 新增 `BootFileLoggingTest`（chat 落盘/查询不落盘）+ `LogbackTestCleanup`（Windows 下 Logback 文件 appender 锁 @TempDir 导致 JUnit "Failed to close extension context"，需在 @AfterEach 释放，已挂到 BootCliChatTest、BootCliRuntimeTest）。
- 验证：`./mvnw -pl oryxos-boot -am test` 全量 40/40 通过。
- 坑：`-pl oryxos-boot` 不带 `-am` 会因本地仓库旧快照报 "junit-jupiter failed to discover tests"，与本改动无关，跑模块测试要带 `-am`。
